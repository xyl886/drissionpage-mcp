# 10 · 请求模式与双模式

DrissionPage 有三个页面类，**选错会让程序慢十倍或写不出来**。

## 三选一：先看需求

| 需求 | 用谁 |
|---|---|
| 需要 JS 渲染、点击、登录交互、抓浏览器内的接口 | `ChromiumPage`（浏览器模式） |
| 接口已摸清，只需 HTTP 请求 + 解析 | `SessionPage`（请求模式） |
| 既要浏览器登录，又要复用登录态纯请求抓数据 | `WebPage`（双模式）或 `dp_transfer_cookies` |

实测分布（本地 462 个采集脚本）：`ChromiumPage` 71 次、`WebPage` 31 次、`SessionPage` 5 次。
也就是说**浏览器模式仍是主力**，请求模式用于「已摸清接口后提速」。

## SessionPage（请求模式）

不启动浏览器，底层就是 requests.Session。

```python
from DrissionPage import SessionPage, SessionOptions

so = SessionOptions()
# 注意：SessionOptions 没有 set_proxy（单数），正确的是 set_proxies（复数）
# 只传 http 时 https 仍为 None，要两个协议都走代理必须都传
so.set_proxies(http='http://127.0.0.1:7890', https='http://127.0.0.1:7890')
# 注意：so.headers 是只读 property，直接赋值会 AttributeError
so.set_headers({'User-Agent': '...'})   # 或用 so.set_a_header(name, value)
so.set_timeout(15)
so.set_retry(times=2, interval=1)       # 注意：这里是单个 set_retry，不是 set.retry_times

sp = SessionPage(session_or_options=so)
sp.get('https://api.example.com/list?page=1')

sp.json          # 响应是 JSON 时直接给 dict；不是 JSON 时返回 None（不抛异常）
sp.html          # 响应文本
sp.title
sp.response.status_code
```

定位接口与浏览器一致（返回 `SessionElement`）：

```python
sp.eles('css:.item')          # 同样返回可读元素
sp.ele('@id=title').text
```

请求与关闭：

```python
sp.get(url, retry=2, interval=1, timeout=15)
sp.post(url, data={'k': 'v'})
sp.close()
```

`SessionPage` 只封装了 `get` / `post`。要发 PUT/DELETE 等，直接走底层 session：

```python
resp = sp.session.request('PUT', url, json={'k': 'v'}, timeout=15)
```

## WebPage（双模式）与实测坑

`WebPage` 继承 `ChromiumPage`，同时具备请求能力，可以在两种模式间切换并互相转交 cookies。

### ⚠️ 坑 0：同一个浏览器只对应一个页面对象（单例）

**这是最容易踩的坑，先看它。**

实测（4.0.5.6）：

```python
p = ChromiumPage()       # 默认端口 9222
w = WebPage()            # 也默认 9222
print(w is p)            # → True ！拿到的就是同一个 ChromiumPage
print(type(w).__name__)  # → 'ChromiumPage'，根本不是 WebPage
w.change_mode('s')       # ✘ AttributeError：ChromiumPage 没有 change_mode
```

同一个浏览器（同端口 / 同 user_data_path）**只会创建一个页面对象**：
后建的对象若指向同一浏览器，会把已有对象直接返回。于是 `WebPage` 独有的
`change_mode` / `cookies_to_session` 全都拿不到 —— 而且**不报错**，
只是类型悄悄变了、能力悄悄少了。

**两种正确做法**：

```python
# 方案一：脚本里只用 WebPage，不要同时创建 ChromiumPage
wp = WebPage()                        # 干净起手，拿到的确实是 WebPage
wp.get(url)
wp.change_mode('s', go=False)

# 方案二：给 WebPage 一个独立浏览器（独立端口）
from DrissionPage import ChromiumOptions
wp = WebPage(chromium_options=ChromiumOptions().auto_port(True))
```

这也解释了为什么「先 ChromiumPage 抓页面、再 WebPage 转请求」行不通。
真要在两者间复用登录态，用 MCP 的 `dp_transfer_cookies`
（把浏览器 cookies 灌进请求模式），或按本文末的「登录一次、纯请求抓全量」流程。

### ⚠️ 坑 1：`WebPage(mode='s')` 的构造参数不生效

实测：

```python
WebPage(mode='s').mode    # → 'd'  （仍然是浏览器模式！）
WebPage(mode='d').mode    # → 'd'
```

`mode` 构造参数**不会**把你带进请求模式。不要指望它。

### ⚠️ 坑 2：没访问过页面时 `change_mode('s')` 会抛异常

```python
wp = WebPage()
wp.change_mode('s')
# → ConnectionError: s模式访问失败，请设置go=False，自行构造连接参数进行访问。
```

原因是 `change_mode` 默认 `go=True`，会拿**当前 URL** 重新访问一次；而刚构造的
`WebPage` 还没有 URL。

### ✅ 两种正确切法

```python
# 切法一：显式 go=False（不自动访问）
wp = WebPage()
wp.change_mode('s', go=False)      # mode = 's'
wp.get(url)                        # 之后再请求
wp.change_mode('d', go=False)      # 切回浏览器模式

# 切法二：先在浏览器模式访问过页面，再切
wp = WebPage()
wp.get(url)                        # 此时 mode = 'd'
wp.change_mode('s')                # 有 URL 了，go=True 会用它重新以请求模式访问 → mode = 's'
```

### cookies 互转

```python
wp.get('https://site.com')     # 浏览器模式完成登录
wp.cookies_to_session()        # 把浏览器 cookies 交给内部 requests 会话
wp.change_mode('s')            # 切到请求模式
wp.get('https://site.com/api/data')   # 带着登录态直接请求，不渲染
```

反向：`wp.cookies_to_browser()`。

实测 `cookies_to_session()` 在 `d` 模式下直接调用是**允许**的（不抛异常）。

## MCP 里怎么做

MCP 没有暴露 WebPage 对象本身，而是把「最有用的一步」做成了独立工具，
避免两套页面对象互相干扰：

| 需求 | MCP 工具 |
|---|---|
| 纯请求 | `dp_session_request(url, method, ...)`（`parse_html=true` 会返回 `root_id`） |
| 读请求模式的 cookies | `dp_session_cookies` |
| 设置请求默认头 | `dp_session_set_headers` |
| **请求会话运行时配置**（代理 / 超时 / 重试 / 编码 / 校验 TLS 等） | `dp_session_set`（不传参数会被拒；`clear_proxies=true` 清空代理） |
| 关闭请求会话 | `dp_session_close` |
| **浏览器登录态 → 请求模式** | `dp_transfer_cookies(direction='to_session')` |
| 请求模式 cookies → 浏览器 | `dp_transfer_cookies(direction='to_browser')` |

典型「登录一次、纯请求抓全量」流程：

```
dp_browser_connect(headless=false)
dp_navigate(url="https://site.com/login")
# … 人工或脚本完成登录 …
dp_transfer_cookies(direction="to_session")     # 登录态灌进请求模式
dp_session_request(url="https://site.com/api/list?page=1", parse_html=true)
dp_find_elements(root_id="…", selector="css:.item")
```

这样只启动一次浏览器（用于登录），后续全部走请求，速度快得多。

## 选型建议

1. **新站点先上浏览器**：结构、渲染方式、反爬都不清楚时，浏览器模式最省事。
2. **看清接口后再转请求**：用 `dp_listen_*` 摸清 URL、参数、签名，再评估能否纯请求复现。
3. **签名复杂的别硬转**：参数由 JS 加密生成时，保留浏览器模式更稳；纯请求复现
   加密逻辑的成本往往高于直接用浏览器。
4. **cookies 有时效**：转交后长时间跑要注意会话过期，命中 401/403 就重新登录再转。
