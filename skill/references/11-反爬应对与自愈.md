# 11 · 反爬应对与自愈

> 本文模式提取自真实采集项目（站点包括商超、招聘、行情、B2B 目录等）。
> 反爬不是「写一次就完」的问题，而是**运行期的不确定性**：同一个脚本
> 昨天能跑、今天被拦。所以工程上的答案不是「找到绕过技巧」，
> 而是**让任务在被拦时能自己恢复并继续**。

## 反爬的三种典型表现

| 表现 | 特征 | 处理 |
|---|---|---|
| 硬拦截 | HTTP 403/429，页面文本含 `Access Denied`、`Too many requests` | 退避 + 重开浏览器 |
| 挑战页 | `Just a moment...`、`Checking your browser`、`verify you are human` | 退避（或人工过一次），不要硬刷 |
| 静默降级 | 200 正常返回，但内容是空列表 / 缺字段 / 登录态失效 | 校验业务字段，而非只看状态码 |

第三种最危险 —— 状态码正常、脚本不报错，但数据全是空的，很容易污染结果库。

## 特征识别

把「被拦」的判定收敛成一组文本标记，命中任一即认定被拦截：

```python
block_markers = (
    'Access Denied',
    'Too many requests',
    'are you a robot',
    'verify you are human',
    'Request unsuccessful',
    'Just a moment',
    'Checking your browser',
)

def looks_blocked(page):
    text = page.ele('tag:body').text or ''
    low = text.lower()
    return [m for m in block_markers if m.lower() in low]
```

要点：

- **大小写不敏感**匹配（站点大小写不统一）；
- 加一个**空内容判定**（关键字段为空也视为异常），覆盖静默降级；
- 判定函数返回命中的标记，便于日志定位到底是哪种拦截。

MCP 里直接用 `dp_check_blocked`：内置了这套默认特征集，也支持传自定义 `markers`，
还能离线检查已落盘的 HTML（`dp_check_blocked(html=...)`）。

## 自愈循环骨架

核心结构是「失败 → 关闭浏览器 → 退避等待 → 重开 → 原地续跑」：

```python
class Collector:
    retry_min_wait = 180      # 首次退避（秒）
    retry_max_wait = 14400    # 退避上限（秒）= 4 小时
    retry_backoff = 2         # 每次翻倍
    common_error_wait = 30    # 非反爬异常的短等待
    common_error_limit = 3    # 非反爬异常连续多少次就跳过该点

    def ensure_page(self):
        """确保有一个可用的、未被拦截的页面。"""
        wait = self.retry_min_wait
        while True:
            try:
                self.open_page()                    # 内含 looks_blocked 检查
                if self.looks_blocked():
                    raise BlockedError('命中阻断特征')
                return
            except Exception as exc:
                self.log.warning(f'[自愈] 页面不可用：{exc}，等待 {wait}s 后重开')
                self.safe_quit()                    # 关掉浏览器，别让它带着坏会话
                time.sleep(wait)
                wait = min(wait * self.retry_backoff, self.retry_max_wait)

    def safe_quit(self):
        page = getattr(self, 'page', None)
        if page is not None:
            try:
                page.quit()
            except Exception:
                pass
        self.page = None
        self.current_point = ''                     # 清掉「当前进度点」，重开后会重试该点
```

### 参数设计要点

1. **退避要真的指数增长**：`wait = min(wait * 2, 上限)`，别写死固定间隔。
2. **单位要与注释一致**：`retry_max_wait = 360` 配注释「4 小时」是错的（那是 6 分钟）。
   这类不一致会让线上行为与预期差两个数量级 —— 实测项目里踩过。
3. **区分「反爬」与「代码 bug」**：反爬要长退避；选择器失效、解析异常这类
   是自己的问题，长退避只会浪费时间，应该短等待后跳过该点继续。
4. **重开浏览器要清空进度点**：否则会带着「上次失败的上下文」继续，导致连环失败。
5. **退避期间要落盘进度**，进程被 kill 也能续。

## 会话失效的识别

登录态类站点（电商、B2B 目录）表现为「突然跳到登录页」或「接口返回未认证」：

```python
def ensure_logged_in(page):
    if '/login' in (page.url or '') or page.ele('@class:login-form'):
        refresh_login(page)          # 重新登录（或读 cookies 注入）
```

比识别更重要的是**别把失效当正常**：很多脚本把空结果写库后发现整批数据是空的。

## 单点失败隔离

长循环里，一页失败不能毁掉全量：

```python
for url in urls:
    if url in done:                  # 断点续采：跳过已完成
        continue
    try:
        record = collect_one(url)
    except BlockedError:
        ensure_page()                # 反爬：长退避后继续（不推进进度点）
        continue
    except Exception as exc:
        logger.warning(f'{url} 解析失败：{exc}')   # 自身问题：记录并跳过
        continue
    save(record)
    done.add(url)
    dump_progress(done)              # 逐项落盘
```

关键点：

- **反爬异常与普通异常分开处理**（一个退避重试，一个跳过）；
- **每成功一项就更新进度**，而不是最后统一写；
- **页面对象可能已损坏**：捕获异常后必要时 `page.quit()` + 重开，而不是继续用同一个 tab
  （坏 URL 或导航失败后 `ele()` 可能抛 `PageDisconnectedError`）。

## 配置层的缓解手段

这些是「降低被拦概率」，不是绕过：

```python
co = ChromiumOptions()
co.set_user_data_path('./profile')     # 复用登录态与历史，比全新环境更「像真人」
co.set_proxy('http://127.0.0.1:7890')  # 换出口 IP
co.no_imgs(True)                       # 减少无用请求
co.set_user_agent('真实浏览器 UA')
co.auto_port(True)                     # 多实例隔离身份
```

节奏上：

- 请求之间加**随机**等待（`page.wait(1.5, 3.0)`），不要固定间隔；
- 大任务拆批次，批间长休；
- 优先走接口而不是页面：能纯请求就别驱动浏览器。

## 不要做的事

| 做法 | 问题 |
|---|---|
| 被拦了就疯狂重试 | 只会加深风控标记 |
| 用 `by_js=True` 硬点验证码 | 事件 `isTrusted=false`，多数风控能识别；且治标不治本 |
| 固定 sleep 循环高频请求 | 规律性最容易触发限流 |
| 无限制重试不退避 | 任务永远卡在同一个点，还不落盘 |
| 只看状态码判断成功 | 静默降级会被当成功，污染结果库 |

## 与 MCP 的对应

| 能力 | MCP 工具 |
|---|---|
| 检测是否被拦（在线 / 离线） | `dp_check_blocked(html=..., markers=...)` |
| 一步恢复：关浏览器 → 退避 → 重开 → 回原地址 | `dp_blocked_recovery(seconds=..., url=...)` |
| 长任务落盘与续采 | `dp_get_html` / `dp_save_page` 配合离线解析（见 `09-离线解析与断点续采.md`） |
| 观察请求是否异常 | `dp_listen_start` + `dp_listen_wait` |

典型自愈循环（MCP 侧）：

```
dp_navigate(url=...)
dp_check_blocked()                      → blocked=true 且 matched=[...]
dp_blocked_recovery(seconds=600, url=...)
dp_check_blocked()                      → blocked=false，继续采集
```

**注意**：MCP 单次调用是同步阻塞的，`seconds` 设为几十分钟会让客户端超时。
真正需要长退避的大任务，建议写成脚本（在脚本里做完整的退避循环），
把 MCP 用在「探索与验证」阶段。
